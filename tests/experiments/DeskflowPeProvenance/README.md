# Deskflow 历史核心：隔离重新链接与 PE 比较

本材料只核验 **Windows x64 多设备测试核心**的链接证据。它不启动程序，不修改输入，不证明运行行为、所有历史源码的时点状态、动态库来源或发行许可。不要将其与 0.1.9 单设备核心或 macOS 官方核心混为一谈。

## 本次证据

在独立目录重链接现存历史构建对象和项目静态库，复用现存 MSVC、Qt 和 OpenSSL 导入库及系统 SDK 库；链接前后这些输入文件的 SHA-256 均未改变。输出未启动。旧测试核心 SHA-256 `04ce02fb644b2e3e80a23f50077aaca1168c5a1ea520e5d45e48aa68104cfffa`；新链接结果为 `dca5d90b199f76b7ecb023aaa551b5ee14768962da9f4505bf9253552e4efdf7`，均 1,117,696 字节。两文件有 6 个字节不同，全部位于合法解析出的 PE 文件头时间戳和唯一调试目录时间戳字段；仅在内存中将各自这两个字段置零后，文件逐字节一致，归一 SHA-256 均为 `4394c285307a6a2d1c25667ae6d68a7a994fd1ef92e222b217758766d84ec143`。机器可读记录见 [comparison-evidence.json](comparison-evidence.json)。项目对象、导入库的链接前后摘要以及链接后检查的系统库、工具摘要，见脱敏的[链接输入清单](link-input-manifest.json)；系统库和工具只有链接后的记录，不能证明其历史时点内容。

曾在链接命令尝试传入历史时间戳，但最终产物的时间戳仍不同，原因未确认；因此不能声称原始二进制哈希完全复现。已有的源码树和 COFF 取证提供额外支持，但时间戳、当前构建对象和当前源码均可被更改；不能单凭这些材料推断编译当时的每一项输入。

## 复查与安全边界

需要可信可读的历史构建目录及其对象、静态库、资源、清单、精确链接工具及依赖库。在旧构建目录运行只读查询 `ninja -t commands bin/deskflow-core.exe`，最后一条为该目标的链接命令（查询输出可能包含路径）；只读取旧目录，准备全新工作目录，逐项记录输入 SHA-256，将链接器 `/out`、`/implib`、`/pdb`、CMake `vs_link_exe --intdir` 以及 `TEMP` / `TMP` 全部指定到新目录，再按命令原有顺序使用已核验输入。该命令可能包含本机路径，分享前必须审查；路径、Qt 和 SDK 等都需根据实际环境指定。不要在旧目录直接执行会修改产物的构建命令，不能拿新输出替换现用正式版。复用本机编译器及系统 SDK 的链接不是新机器干净源码构建。

比较两个已取得的 x64 PE 文件：

```text
python -B -m unittest -v test_compare_pe.py
python -B compare_pe.py <历史核心> <隔离重链接核心>
```

工具只读两个输入，不执行或修改文件，不输出输入路径；输出的 JSON 包含原始哈希、不同字节数、字段偏移和归一哈希。成功且归一后相同返回 0；归一后不同返回 1；损坏、不受支持或无法读取返回 2。解析器刻意只接受 x64 PE32+、唯一且可唯一映射的调试目录，两处时间戳必须相同；其他合法但不同布局也会被拒绝。它检查结构边界和节重叠，不能作为完整 PE 安全校验器。不要使用它来掩盖除两处时间戳以外的差异。
