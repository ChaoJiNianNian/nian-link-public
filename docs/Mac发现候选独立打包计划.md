# Mac 局域网发现候选：独立打包与隔离计划

## 目标与现状

在不覆盖现用正式版或旧多设备测试版的前提下，准备独立的 Mac 发现测试候选。Windows 双机发现、配对和键鼠切换已由用户实测一次；Mac 独立候选已在 Mac 上启动，真实发现尚未验收。此计划不授权覆盖、删除现有 App、配置或钥匙串条目。

## 隔离方案

1. 新候选将使用独立入口项目、构建中间目录和输出、独立显示名称与 bundle ID `com.niannian.nianlink.discovery-test`；保留现有正式与多设备候选的入口、身份和行为。入口项目应正确包含既有多设备 UI 和资源，并与独立发现组件显式链接；验证 Avalonia 资源名及完整依赖图。编译符号和打包模式必须互斥，禁止使用可能互相覆盖的共享中间目录。
2. 首次发现实测优先复用现有多设备候选的显式 `--data-dir` 入口，放在为本次实测原子新建、随机命名的测试父目录内；资料子目录单独以不可覆盖方式创建。暂存前后核对链接、所属用户、权限和路径，并拒绝与已知正式、旧候选目录重叠；不接管任何已有目录。启动检查仍使用尚不存在的新路径。此前 `DiscoveryCandidate` 固定路径判定保留原样，不直接作为本次随机资料目录的入口。此方案针对正常并发及已有目录冲突；不声称防御同权限进程在路径检查后恶意替换目录，现有存储层仍使用路径而非持有的目录句柄。
3. 独立钥匙串服务 `app.niannian.nianlink-discovery-test.identity.v1` 必须由发现候选明确注入；旧服务 `app.niannian.nianlink-standalone.identity.v1` 不变。禁止运行时接受任意服务名或回退到旧身份；实际接入时检查所有身份打开路径。隔离的路径及独立服务都不代表已完成实际 Keychain 测试。
4. 发现原生桥应由源码在隔离目录构建，核对架构、来源、哈希和构建证据，随新候选复制并验证；不得把临时探针、个人资料、私钥或未经确认的辅助文件打入包。构建脚本要选择新入口项目真实的还原依赖清单，而非硬编码旧项目的 project.assets.json；不改写正式资源或旧候选产物。
5. 打包和暂存脚本以明确且互斥的新模式校验专属 bundle ID、显示名称、manifest、包内文件、Mach-O UUID 和路径；随机新目录中解压后才允许对新候选临时 ad-hoc 签名，并严格核验。区分未签名构建清单与最终签名后的文件校验；不触碰其他已安装 App、不重置系统权限。此测试签名不等同于开发者签名或公证。
6. 候选专属本地网络说明应清楚告知用户只有主动开启发现时会在局域网暴露设备名称、系统类型与公钥指纹；权限交由 macOS 和用户处理。不得把命令行探针的权限结果视为 App 权限，不能记录 SSID、BSSID、MAC 地址或身份秘密。

## 分步验收

1. 先以无网络、无 Keychain 的测试验证路径规则及受限服务选择，并回归现有启动行为。本增量只增加尚未接入产品入口的策略，不能生成可用发现 App。
2. 完成网络绑定原生桥与受控失败、变化失效测试，再集成候选入口；真实系统查询、网络接口绑定与发现生命周期均须分别检查。
3. 在隔离输出中构建并校验包、依赖、架构、文件和签名；检查正式与旧候选产物不变。每一步保持可撤销，不提交或推送。
4. 仅从核验过的新候选路径启动，实际检查系统权限、身份隔离、发现开关与停止、网络变化及异常，再进行用户参与的 Mac/Windows 发现、指纹核对、配对和控制实测。不要自动停止或修改已有 Deskflow 进程；处理可能的端口冲突。没有实际完成的项目不能报告为通过。

## 第三增量：独立可运行入口

创建独立 `NianLink.MacDiscoveryCandidate` 项目，引用现有 Mac 多设备界面源码及资源，固定专用编译标志并拥有自己的中间目录；禁止把未完成的发现模块接入。入口要求显式指定 `~/Projects/nian-link-test-<32位小写十六进制>/profile`，启动检查使用同一隔离父目录下不存在的 `startup-check-<32位小写十六进制>`。检查路径、受保护资料目录与符号链接，并在进入界面之前失败关闭；测试资料目录由暂存脚本独占创建并核验。编译标志仅让新入口使用发现专属 Keychain service 和专属显示名称，旧版默认行为不变。先写路径、身份与编译隔离测试，再实现、独立审查和交叉构建；不访问 Mac 或真实 Keychain。

打包并行增量将使用独立 bundle ID、显示名称、manifest、Mach-O UUID 和该入口自身的还原依赖清单，互斥现有打包模式；暂存以新目录独占创建、核验资料路径，不覆盖已安装应用。该阶段只验证入口及打包，不代表发现、权限或双机功能已通过。

## 真实桥接入与签名顺序

Mac 已在独立目录验证，bridge 单独 ad-hoc 签名会改变 SHA；`codesign --deep --force` 会强制重新签名嵌套代码，不能沿用签前摘要。仅发现候选允许输入已签 bridge 副本，构建前核对文件位置和 SHA，并以该签后 SHA 作为 `NianWifiEvidencePinnedSha256` 编入候选网络程序集；复制后核对 `Contents/MacOS/libNianWifiEvidence.dylib`。暂存时逐一签其他 Mach-O、验证但不重新签 bridge，最后签应用外层；对整个 App 做 deep 验签并再次核对 bridge SHA。签名后任何不匹配直接失败，旧候选签名路径不改。包内 manifest 的编译摘要与实际文件关联、签名行为和 `AppContext.BaseDirectory` 须分别测试；签名是临时 ad-hoc 测试，不等于公证或 Developer ID，哈希检查到加载仍有替换窗口。Apple 建议由内向外签名而非使用 deep 签名： https://developer.apple.com/documentation/xcode/creating-distribution-signed-code-for-the-mac/ 。

- 2026-11-12：已用独立签后桥生成包含发现 UI 和真实应答适配的候选包，位于 `.artifacts/mac-package/test-2386b4f5115b466cab43aa726466972a`，ZIP SHA-256 为 `3f24ec365ea693991be7be519cbe16f8b9e214846b10d1a80f56af33f0419fb6`。发布程序集嵌入的唯一 pin 与包内 bridge 签后 SHA 一致，已由独立只读审查复核。
- 暂存签名流程的保护措施已通过模拟和篡改测试；实际 Mac App 的逐项签名、最终 bridge 不变、App 加载与联网权限仍待实测。此包不覆盖已有 App，也尚未通过双机发现与配对验收。

## Mac 暂存签名失败与修复（2026-11-12）

- 首次隔离暂存签名未成功，也未启动 App；失败目录保留。签名主程序时系统提示 `System.Net.WebSockets.Client.dll` 未签名。现场 `file` 与本地字节核对确认它是 .NET PE 托管程序集（MZ），不是 Mach-O；此前脚本只签 Mach-O，且按文件名排序过早签主程序。不能仅改变主程序排序就声称已解决。
- 本次内部验证方案：在新隔离目录解压后，先识别并逐个签名托管 PE DLL，再签其他 Mach-O 子组件（不重签已验证的 bridge），最后签整个 App，不单独预签主 apphost；随后 deep strict 验签，并复核 bridge 签名和原固定 SHA。PE 文件的签名可能依赖 macOS 扩展属性，普通 ZIP 不保留；这里在 Mac 解压后签名，不将签后 App 重新打普通 ZIP。先模拟验证签名顺序、错误和篡改，再由主任务用新目录实际检查；失败仍停止，不能将模拟结果当成实际签名成功。
- Apple 将 `Contents/MacOS` 视为代码位置，对非 Mach-O 文件签名使用扩展属性，且推荐资源放在 `Contents/Resources`：https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/Procedures/Procedures.html 。本次为隔离功能验证保留当前 .NET 布局，正式发行时需另行设计规范布局与依赖加载。
- 修复后，隔离 Mac 上对单个 PE DLL 副本的签名和严格验签各成功一次；完整 App 尚未验证。脚本已按上述顺序调整，独立只读复审未发现确定的静态阻断，相关 Python 测试 77 项运行、76 通过、1 跳过；签名失败即停止，不执行 App 外层签名或启动。
- 第二次全包隔离暂存时，207 个 PE 和其他 Mach-O 均完成签名，但外层 App 签名在 `Contents/MacOS/CollaborationUi/mini.js` 处报未签名，App 未启动，失败目录保留。该文件独立副本的签名和严格验签随后在 Mac 各成功一次；脚本现先签 `Contents/MacOS` 中全部非 Mach-O 普通文件（包括 JS、HTML、CSS、JSON 和 PE），再签其他 Mach-O、外层 App 并复核 bridge。78 项 Python 测试中 77 项通过、1 项跳过；完整 App 的第三次签名结果仍待实测。
